# AGENTS.md - Bidbrain Analytics (canonical agent guide)

Monorepo of self-hosted client marketing dashboards on GCP. One repeatable pattern, many clients:
**MongoDB is the template**; **STT** is the archetype every lean paid-media client is copied from;
**geocon** is the template for lean Meta clients. **13 client dashboards are LIVE** (+2 live
placeholders), plus the **platform front-door** (dashboards.bidbrain.ai), the
**status pipeline** (data-health monitoring), and **The Grid** (`grid-core/`, the internal agency
cockpit, service `central-grid`, proxied super-admin-only at `/d/central/`).

**This file is the canonical shared-agent doc**, read natively by Codex/Kimi/most coding agents;
Claude Code loads it through the one-line `@md/AGENTS.md` import in root `CLAUDE.md` (this file
lives in `md/`; other agents that only look at the repo root will not find it unless pointed here).
Keep it LEAN:
repo-wide rules and fixed facts ONLY. Depth lives one level down, and an agent should complete a
routine task **from the docs alone, scanning nothing**:

- Any client task -> `clients/client_<c>/README.md` (file map, data contract, cookbook, gotchas).
- Team sync / branches / deploy flow -> `scripts/README.md` (start_day, park, push, ship, go).
- Platform front-door -> `bidbrain-platform/README.md`. Status pipeline -> `status_dashboard/README.md`.
- The Grid -> `grid-core/README.md` (+ `GRID_SPEC.md`). Ingest loaders -> `ingest/<unit>/README.md`.

## Fixed facts (memorize; never re-derive)
- GCP project: `bidbrain-analytics` (project # 516554645957)
- Region: `australia-southeast1` - **EVERYTHING**, never another region.
- Artifact Registry docker repo: `bidbrain` (shared by all clients)
- Local dev: Windows + PowerShell 5.1. Use the repo venv: `.\.venv\Scripts\python.exe`
- **gcloud config is pinned per VS Code window** via the `CLOUDSDK_ACTIVE_CONFIG_NAME` env var
  (this repo's window = config `personal` -> `ian@100.digital` / `bidbrain-analytics`; the separate
  Agora window uses config `agora`). **Never** run `gcloud config set account/project` or activate
  configs - pass `--project=... --account=...` explicitly for a one-off cross-project command.
  (`scripts/start_day.ps1` is the sanctioned exception: it pins the env var for its own process
  first, so its sets can never clobber the agora window.)
- Git: `origin` (github.com/ianfernandez581/bidbrain-analytics) is the ONLY live remote. The old
  `bidbrain` remote (github.com/Bidbrain/...) is dead (404); start_day removes it if found.
- Per client `<c>` everything derives from the key: dataset `client_<c>`, bucket
  `bidbrain-analytics-<c>-dash`, export job `<c>-export`, web service `<c>-dash`.
- Windows PS 5.1 gotchas: no `&&` / ternaries; `gcloud run deploy` hangs on the unauthenticated
  prompt (always `--no-allow-unauthenticated --quiet`); `Get-Content | bq query` corrupts UTF-8
  SQL (use the client's `create_views.py`); quote `--set-secrets=` values (PS mangles bareword
  commas); keep `.ps1` files pure ASCII (a no-BOM em-dash decodes to a curly quote under WinPS 5.1
  and can break parsing).
- **DTS bridge views have frozen `last_modified`**: `raw_google_ads.perf_google_ads` and
  `raw_ga4.perf_ga4(+events)` are VIEWS whose `__TABLES__.last_modified` never moves. NEVER gate or
  probe freshness on them - use the native base TABLES (the partitioned `p_ads_*_<customerid>`
  twins for Google Ads; the `ga4_*_<property>` tables for GA4) or the `raw_windsor.*` fallbacks.

## The data contract - when an edit needs NEW data, not just layout
A value on screen traces through three files, matched **by name**:

    sql/*.sql view column  ->  job/main.py (env={...} dict key)  ->  dashboard.html (data.* key)

"Add metric X" = three edits: surface it in the right `sql/*.sql` view, expose it in `job/main.py`,
render it in `dashboard.html`. Editing only the HTML renders nothing; renaming a key anywhere
breaks the next stage - fix both ends. Each client README carries its concrete contract table.

## Campaign names are NOT stable keys (2026-08-04, repo-wide)
Transmission is progressively prefixing campaign names with the brief number (`1160_`, `2103_`,
`2265_`, `2306_`, `2479_` ...). Consequences, all of which have bitten in production:
- **Fixed-offset `SPLIT` parsing shifts by one field.** A market token becomes `APAC-ANZ` instead of
  `ANZ`. It is non-empty, so `<> ''` guards still pass and rows survive the model - they just match
  no dashboard chip and disappear from every KPI, chart, table, CSV and AI deck. Silent.
- **Exact-name matches and `STARTS_WITH` break outright** (cloudflare's per-campaign LinkedIn dashes
  and the status checks key on exact `CAMPAIGN_GROUP_NAME`; a rename zeroes them).
- **The same campaign exists under BOTH name forms in the feed**, so any name-keyed aggregate splits
  in half until the old form ages out.
**Rule: never key off a raw campaign name.** Strip the prefix once in the staging view
(`REGEXP_REPLACE(TRIM(CAMPAIGN_NAME), r'^[0-9]+_', '') AS CAMPAIGN_NAME_NORM`) and point every
offset, `LIKE`, `STARTS_WITH` and market `CASE` at that. Reference impl: `clients/client_cloudflare/
sql/01_stg_linkedin.sql` + `03_stg_tradedesk.sql`.
**Audited repo-wide 2026-08-04** (`grep -n 'SAFE_OFFSET\|SPLIT_PART' clients/**/*.sql`):
- FIXED: cloudflare (`03_stg_tradedesk`, `01_stg_linkedin`), mongodb (`01_stg_tradedesk`,
  `11_stg_tradedesk_pixel`).
- NOT AFFECTED, do not "fix": **schneiderlqai** scopes on the `%LQAIDC%` substring and parses country
  with `CONTAINS_SUBSTR`; **schneider** matches `seed_campaign_map` tokens with `STRPOS` and parses
  market with boundary regexes; **caltex** splits ad-group names on `|`, not `_`. Substring and token
  matching are inherently prefix-proof - only FIXED OFFSETS and EXACT-NAME equality break.
- A `CASE ... ELSE '<default>'` on a parsed token is the dangerous shape: it converts a parse break
  into silent misattribution instead of an error (that is exactly how mongodb's pixel view hid it).
**And never let an accuracy check mirror the view's own parse** - it goes circular and stays green
while delivery vanishes (exactly what happened here). Check the whole advertiser/account total
against the dashboard total instead, so a parsing regression cannot hide.

## Freshness contract (binding for every export job)
Every dashboard must refresh within ~10 min of its upstream updating - via a SELF-GATING job on a
`*/10` Cloud Scheduler tick that probes upstream freshness and only rebuilds when something
advanced past its watermark (`_freshness.json` sidecar in the client bucket; `FORCE_REBUILD=1`
bypasses). Gate source = whatever the job READS: Snowflake-direct probes
`INFORMATION_SCHEMA.TABLES.LAST_ALTERED` (metadata-only, never resumes the warehouse); BQ-reading
jobs probe `__TABLES__.last_modified_time`. Never watermark a VIEW (frozen `last_modified` - see
the DTS bridge-view fact above). Upload first, write watermark second. New clients vendor
`job/freshness.py` and inherit this. Dashboards show `last_updated` + `data_through`, never a
hardcoded refresh time.

## Team flow - start_day / park / push / ship / go (full doc: scripts/README.md)
Slash commands are thin Claude Code wrappers in `.claude/commands/`; **every other agent or human
runs the same `.ps1` directly for identical behavior**:
- `/push` -> `scripts\push-branch.ps1` - commit ALL local work to your own `<dev>/<desc>` branch
  (secret guard blocks key-looking files). Run FROM a `wip/*` branch it PROMOTES the parked work.
- `/ship` -> `scripts\merge-branches.ps1` - integrate every dev branch (SKIPS `wip/*` parked
  branches, reports the count), sanity-gate (conflict markers + Python syntax + JSON + secret
  filenames), land on main, auto-deploy changed services, prune. On conflict it STOPS with the
  conflict in-tree: resolve semantically, `git add -A; git commit --no-edit`, re-run with `-Resume`.
- `/go` - push mine, then ship everyone (its ship half integrates EVERY dev branch, not just yours).
- `/park` -> `scripts\park.ps1` - commit + push WIP to `wip/<dev>/<desc>` WITHOUT shipping; re-park
